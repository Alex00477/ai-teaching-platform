# 技术方案

## 文档职责

本文档记录 P0 的技术基线、数据边界、异步任务、部署方式和来自需求的工程约束。它不重新定义业务规则；冲突时以 [业务规则](业务规则.md) 为准。

## 技术基线

采用“模块化单体 + 独立 Worker”，先满足可验证的 P0 闭环，不提前引入微服务。

| 层次 | 选择 | 责任边界 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 角色化页面，不直接访问 PH8 |
| API | Python 3.12 + FastAPI | 认证、授权、业务接口、文件访问、任务创建 |
| 数据库 | PostgreSQL | 业务实体、状态和任务的事实来源 |
| 缓存/限流 | Redis | 热点查询、短期缓存和限流；不可保存唯一业务数据 |
| 后台任务 | 独立 Worker + PostgreSQL 持久化任务表 | 领取任务、调用 PH8、写回状态和失败原因 |
| 文件存储 | 私有服务器文件卷，封装存储接口 | 保存讲义；访问前由 API 再次鉴权 |
| 模型客户端 | 独立 PH8 Client，OpenAI 兼容协议 | 统一密钥、超时、错误映射和响应校验 |
| 部署 | Docker Compose 单机 | 编排 API、前端、Worker、PostgreSQL、Redis |

```text
浏览器 → React → FastAPI → PostgreSQL
                         ├→ Redis（缓存/限流）
                         ├→ 私有文件卷（讲义）
                         └→ ai_tasks（持久化任务）
                                  ↓
                              Worker → PH8
```

## 数据边界

核心实体包括 `users`、`registration_codes`、`classes`、`class_memberships`、`assignments`、`assignment_questions`、`answer_drafts`、`submissions`、`grading_records`、`grading_items`、`ai_grade_tasks`、`explanations`、`teaching_materials` 和 `model_preferences`。

- PostgreSQL 保存业务事实；提交保存答案快照并带作业版本，批改和 AI 任务带关联提交版本。
- 用户名、有效班级关系、同一学生同一作业的有效提交需要唯一约束；运行中的 AI 任务按提交建立唯一约束。认证和班级关系分别由 `001_auth.sql`、`002_classes.sql` 显式迁移。
- 作业、讲义和教师学生搜索的查询必须带权限条件并分页；避免先查全量再在应用层过滤。
- Redis 故障时回源 PostgreSQL，不能因为缓存命中或故障改变权限。缓存键必须包含用户/班级/科目等隔离维度，不缓存 Key、未发布讲义或私人答案。

## AI 批改任务

教师创建任务的请求只做权限、状态、重复任务检查和持久化，然后立即返回任务 ID；页面不等待 PH8。

```text
等待处理 → 处理中 → 待教师确认 → 已确认
                       └────────────→ 失败
```

- Worker 设置超时和有限重试；限流、认证失败、格式错误等不可重试错误快速失败。
- 结果写回前重新校验任务状态、提交快照和作业版本；旧结果不能覆盖人工或新版本。
- 模型输出必须校验结构、题目数量和字段；失败不得产生学生可见正式结果。
- PH8 故障或队列拥塞不能拖垮登录、查看作业、保存草稿和人工批改。

## 安全技术底线

- 会话使用 HttpOnly、Secure、合适 SameSite 的 Cookie；授权始终由服务端会话和数据库判断。
- PH8 Key 只来自服务端环境变量或密钥管理器，不进入前端、Git、日志、普通数据库字段或截图。
- 文件不放在公开目录；列表、详情和下载每次都校验发布状态与班级权限。
- 日志和错误响应过滤密码、恢复码、邀请码、班级码、Authorization、完整学生答案和上游敏感内容。
- 注册、提交、发布讲义、创建 AI 任务和敏感模型调用具备幂等/唯一约束、基本限流和审计。

## 部署与本地启动

当前目录边界：`apps/api`、`apps/web`、`migrations`、`scripts`、`docs`、`decisions`。API 和 Worker 共用一个 Python 包，但以不同进程启动；最小 API、Worker、认证、班级关系、作业发布和学生提交模块已建立，批改和讲义业务仍未实现。

当前本地启动顺序：

1. `docker compose up -d postgres redis`
2. 配置未提交的本地环境变量和会话密钥。
3. 按顺序执行 `migrations/001_auth.sql` 和 `migrations/002_classes.sql`（其他业务迁移尚未创建）。
4. 启动 FastAPI API、独立 Worker 和 Vite 前端。

启动时配置缺失或格式错误应明确失败；启动服务不自动修改生产数据库。`.env` 只存在于本地/部署环境，模板只记录变量名和格式，不记录真实值。

## 需求约束与待测容量

- 需求要求至少支持 500 人同时在线；这表示 500 个有效会话，不等同于 500 个同时请求或 500 个并发模型调用。
- AI 批改必须异步；教师学生搜索需要数据库索引和分页；缓存不能绕过权限。
- 以上是已知约束，不据此臆造 p95/p99、请求量、队列容量或数据规模。服务器规格、真实访问量、PH8 限流和模型处理时间明确后，再制定压测基线。
- 上线前需确认 PH8 基地址/模型/限流/计费、服务器 CPU/内存/磁盘/端口、生产数据库与文件存储是否分离，以及用户自带 Key 是否进入 P0。
